# TUMAR MVP: план реализации

> При переходе к реализации выполнять этапы последовательно с навыком superpowers:executing-plans. Этот документ не запускает разработку. Код, установка зависимостей и создание облачных проектов сейчас не выполняются.

**Цель:** проверить тестовый SOS между реальными Android и iPhone с подтверждением просмотра.

**Архитектура:** одно приложение; Supabase хранит состояние, проверяет права и обрабатывает события. Сохранённые задания запускают push независимо от открытого приложения.

**Стек:** React Native, Expo, TypeScript, Expo Router, Supabase Auth/Postgres/Edge Functions/Realtime, Expo Notifications/Push Service, EAS Build.

**Основание:** [согласованная архитектура](../specs/2026-10-19-tumar-mvp-design.md).

## Общие ограничения

- Пять экранов: вход, главная, доверенный контакт, тревога, настройки.
- Не больше одного принятого доверенного контакта у отправителя; связи направленные.
- Одна активная исходящая тревога на отправителя.
- Все тревоги тестовые, точка заранее задана; доступ к геолокации телефона не запрашивается.
- Подтверждение просмотра не означает оказания помощи; push не гарантирует прочтение.
- Без кулона, подписки, чата, истории маршрутов, встроенной карты и дополнительных продуктовых разделов.
- Зависимости и файлы добавляются только для текущего этапа. Автоматические тесты покрывают критические правила, а не каждую кнопку и отступ.
- Существующее удаление README.md в рабочем дереве не восстанавливать и не включать в изменения без отдельной причины.
- После проверки этапа сохранять отдельный понятный коммит только с относящимися к нему файлами. Не менять посторонние файлы.

## Что проверяем особенно внимательно

1. Возврат из письма подтверждения или восстановления доступа, когда приложение было закрыто: этап 2.
2. Одновременное принятие двух приглашений: второй контакт не появляется, этап 3.
3. Сервер сохранил SOS, но телефон не получил ответ: событие не дублируется, этапы 4 и 6.
4. Push уже показан, но связь отозвана: сведения недоступны, этап 6.
5. На одном телефоне сменился аккаунт: уведомления прежнего аккаунта больше не адресуются этой сессии, этапы 5 и 6.

## Этап 1. Запуск на Android и iPhone

**Результат:** минимальная собственная тестовая сборка открывается на обоих телефонах; техническая возможность push проверена до разработки всех экранов.

- [ ] Проверить исходное состояние репозитория, инструменты, доступ к двум телефонам и аккаунтам сборки. Зафиксировать совместимые версии зависимостей при создании проекта.
- [ ] Подготовить минимальное приложение Expo, конфигурацию окружения и сборок. Исключить секреты из Git; оставить только пример имён настроек.
- [ ] Получить собственные Android- и iOS-сборки. На устройствах проверить запуск, текст, нажатия и повторное открытие.
- [ ] Через тестовый инструмент push проверить регистрацию каждого телефона и получение сообщения в фоне. Это техническая проба без реальных данных и без готового сценария SOS.

**Проверка:** обе сборки установлены и открываются; на обоих телефонах фактически замечено тестовое уведомление. Ошибки подписи, разрешений или учётных записей решены до следующего этапа. Эта проба ещё не доказывает работу серверного оповещения TUMAR.

## Этап 2. Вход и настройки

**Результат:** два человека имеют независимые аккаунты, могут войти и выйти, приложение сохраняет сессию.

- [ ] Настроить Supabase Auth, профиль, доступ только к своему профилю и хранение сессии на устройстве.
- [ ] Реализовать вход, регистрацию, подтверждение email, восстановление пароля и возврат из письма в приложение.
- [ ] Добавить имя и выход в настройки; закрыть доступ к основным экранам без сессии.
- [ ] Проверить реальные письма для тестовых аккаунтов; не считать локальное письмо доказательством внешней доставки.

**Проверка:** два аккаунта видят свои имена; неверный пароль объясняется понятно; сессия переживает перезапуск; выход возвращает ко входу. Ссылки подтверждения и восстановления работают при открытом и закрытом приложении, неверная или просроченная ссылка не даёт доступ. Чужой профиль изменить нельзя.

## Этап 3. Доверенный контакт

**Результат:** пользователь A приглашает B принимать свои сигналы; B явно соглашается.

- [ ] Добавить приглашения и направленные связи, серверную проверку кода и ограничения доступа.
- [ ] Реализовать создание, просмотр отправителя перед принятием, принятие и отзыв. Коды случайные, одноразовые, срок действия 24 часа; попытки ввода ограничены на сервере.
- [ ] Показать направление связи и пустое состояние без контакта.
- [ ] До реализации критических правил добавить проверки самоприглашения, повторного использования, истечения срока, подбора кода и конкурирующего принятия; после реализации убедиться, что они проходят.

**Проверка:** B получает сигналы A только после согласия. Обратная связь сама не создаётся. Два одновременных принятия не дают A двух контактов. Третий аккаунт не видит чужие приглашения и связи. Тестовые запросы к серверу проверяют права независимо от скрытых кнопок интерфейса.

## Этап 4. SOS внутри приложения

**Результат:** полный сценарий работает при открытых приложениях, ещё без автоматической отправки push.

- [ ] Добавить тревоги, получателей и задания оповещения. Запись всех трёх выполняется одной транзакцией; обработчик push пока не включать.
- [ ] Реализовать главную, подтверждение тестовой отправки и экран тревоги с внешними картами.
- [ ] Реализовать подтверждение получателем и завершение отправителем.
- [ ] Подключить обновления активных событий и обязательное перечитывание при открытии и возврате из фона.
- [ ] Проверить серверные права, отсутствие контакта, единственность активной тревоги и повтор одного запроса. Затем проверить тот же сценарий через интерфейс.

**Проверка:** A создаёт тест, B видит его в приложении и подтверждает, A видит время и завершает. Пока тест активен, новый не создаётся. После перезапуска активная тревога остаётся. Посторонний не читает и не подтверждает событие; ссылка карт открывает заданную тестовую точку. Интерфейс не выдаёт сохранение события за отправленный push.

## Этап 5. Серверное push-оповещение

**Результат:** сохранённая тревога запускает push без участия открытого приложения отправителя.

- [ ] Привязать push-токен к текущей сессии; реализовать отвязку при выходе и перепривязку при смене аккаунта.
- [ ] Добавить обработчик сохранённых заданий, немедленный запуск после SOS и периодический подбор оставшихся заданий.
- [ ] Добавить проверку ответов сервиса, удаление недействительных токенов и максимум три попытки для временных ошибок. Не повторять принятую сервисом отправку только из-за отсутствия просмотра человеком.
- [ ] Открывать нужную тревогу из уведомления после проверки сессии и доступа; при необходимости сначала выполнить вход.
- [ ] Показывать отправителю отсутствие зарегистрированного телефона и ошибку оповещения без ложного статуса «Доставлено».

**Проверка:** закрыть приложение B обычным способом, отправить тест с A, увидеть push и открыть правильное событие. Повторить с другой платформы. Имитировать сбой обработчика после сохранения: периодический запуск подбирает задание. Ошибки и повторные попытки сначала проверять на имитации ответов сервиса; реальную доставку — отдельно на телефонах. На экране блокировки нет имени и координат.

## Этап 6. Понятное поведение при сбоях

**Результат:** пользователь видит правдивое состояние, доступ не сохраняется после отзыва связи.

- [ ] Проверить отключённый интернет до отправки и потерю ответа после сохранения события сервером. Сохранять идентификатор попытки локально и сверять результат без создания нового SOS.
- [ ] Проверить восстановление актуального состояния после перезапуска и возврата из фона. Не отправлять новый отложенный SOS автоматически после появления интернета.
- [ ] Добавить в настройки проверку разрешения уведомлений и переход к системным настройкам.
- [ ] Связать отзыв контакта с завершением активного теста, прекращением новых попыток оповещения и потерей доступа получателя.
- [ ] Проверить смену аккаунта на одном телефоне и открытие старого push после отзыва связи.

**Проверка:** отсутствие интернета не выглядит как успешная отправка. Неопределённый результат отображается как проверяемый, после сверки находится то же событие. При отключённых уведомлениях тревога доступна после открытия приложения. Старый push не раскрывает отозванные данные. Токен прежнего аккаунта не остаётся активным для этой сессии.

## Этап 7. Итоговая проверка и передача для демонстрации

**Результат:** воспроизводимая демонстрация на двух телефонах и запись фактических результатов.

- [ ] Пройти всю цепочку Android → iPhone и iPhone → Android в итоговых тестовых сборках, включая установку или обновление и повторный вход.
- [ ] Повторить ключевые проверки фона, закрытия обычным способом, повторного запроса, отсутствия сети, запрета уведомлений и отзыва контакта. Принудительную остановку записать отдельно, без обещания доставки.
- [ ] Выполнить автоматические проверки критических правил, проверку типов и сборку. Исправить выявленные ошибки и повторить относящиеся к ним проверки.
- [ ] В инструкции записать версии сборок, модели телефонов, версии ОС, даты, ожидаемое и фактическое поведение, задержки наблюдаемых уведомлений и ограничения.
- [ ] Подготовить короткий порядок демонстрации: вход → связь → тестовый SOS → уведомление → подтверждение → завершение.

**Критерий готовности:** обе платформы проходят полный сценарий, критические проверки прав и дублей проходят, оставшиеся ограничения перечислены явно. Отсутствие iPhone или аккаунта сборки означает, что iOS ещё не проверен; его нельзя объявить готовым по результатам Android.

## Граница внешнего пилота

Первая приёмка проводится командой на тестовых аккаунтах и фиксированной точке. Перед приглашением внешних участников отдельно проверяются реальные письма, срок хранения и удаление аккаунта и данных. Эти условия не добавляют продуктовых экранов и не превращают прототип в гарантированный экстренный сервис.

## Порядок работы

Начинаем с этапа 1 только после отдельного перехода к реализации. На каждом этапе: минимальное изменение → относящаяся к нему проверка → фиксация результата. Если проверка не проходит, устраняем причину до зависимого этапа. Декоративные улучшения и новые функции не включаем в этот план.

## Уточнение первого запуска

Пользователь сообщил, что доступен Android, но нет iPhone и платного Apple Developer. По последнему запросу первый шаг ограничен запуском через Expo Go на Android: один статический экран, без Supabase, push и дополнительных экранов. Облачные сборки и проверка iOS отложены; исходный критерий готовности обеих платформ пока не выполнен.

Для одного экрана используются App.tsx и index.ts без Expo Router. Router добавляется, когда появятся переходы между экранами. Выбран Expo SDK 57 по текущей рекомендации для Expo Go. Инструкция запуска: [Android](../../run-android.md).

Для текущего этапа контактов выбран один защищённый Postgres RPC вместо отдельной Edge Function: действия работают только с базой и выполняются транзакционно. Добавлен служебный счётчик попыток в третьей таблице. Экран контактов пока открывается сразу после входа без вкладок. Код, SQL и локальные проверки подготовлены; выполнение миграции в проекте пользователя и проверка на двух аккаунтах остаются отдельным шагом. Подробная инструкция: [контакты](../../supabase-contacts.md); английский промпт Stitch: [дизайн контактов](../../design/stitch-trusted-contact-prompt.md).

Пользователь подтвердил выполнение SQL контактов и работу приглашений. Следом согласован тестовый SOS без push и без Realtime: ручное обновление и загрузка при возврате приложения. После входа теперь главная, с переходами к контактам и подробностям тревоги. Минимальные переходы реализованы состоянием React без Router. Для SOS подготовлена следующая миграция, включая служебное соответствие попыток событиям для постоянной защиты от дублей; задан публичный демонстрационный адрес вместо геолокации телефона. Локальные SQL-проверки и Android-экспорт не заменяют выполнение этой миграции и проверку на устройстве. Инструкция: [тестовый SOS](../../supabase-test-sos.md).
