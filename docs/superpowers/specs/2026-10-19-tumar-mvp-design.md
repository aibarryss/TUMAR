# TUMAR: архитектура MVP

Дата: 19 октября 2026 года.

## Согласованная цель и границы

Проверить на реальных Android и iPhone полный сценарий: тестовый SOS → сохранение на сервере → оповещение доверенного контакта → подтверждение просмотра → завершение теста отправителем.

Одна основная кодовая база, одно приложение, пять экранов. Пользователь может одновременно отправлять и получать тревоги. У каждого отправителя не больше одного принятого доверенного контакта; один получатель может получать сигналы нескольких отправителей. Связи направленные: принятие чужих сигналов не даёт права автоматически отправлять свои этому человеку.

Все события помечены как тестовые. Используется заранее выбранная публичная тестовая точка, а не координаты телефона. Подтверждение просмотра не означает оказания помощи. Push не является гарантированным каналом экстренной связи.

## Стек

- React Native, Expo и TypeScript: мобильное приложение.
- Expo Router: переходы между экранами.
- Supabase Auth: email, пароль, подтверждение email, восстановление доступа.
- Supabase Postgres: данные и правила доступа к ним.
- Supabase Edge Functions: доверенная обработка приглашений, SOS и подтверждений.
- Expo Notifications и Expo Push Service: регистрация телефона и push-оповещения.
- EAS Build: собственные тестовые сборки Android и iOS.

Восстановление пароля и подтверждение email — служебные состояния входа, а не самостоятельные продуктовые разделы. Перед внешним пилотом настраиваются реальные письма и ссылки возврата в приложение. Для проверки push нужны собственные сборки и реальные телефоны.

## Общая схема

Приложение → серверная функция → база данных.

Сохранённое задание на оповещение → обработчик уведомлений → Expo Push Service → службы Apple/Google → телефон получателя.

Приложение получателя → подтверждение через сервер → база → обновление состояния у отправителя.

База — источник правды. Push лишь сообщает о событии и содержит идентификатор тревоги; детали приложение получает после проверки доступа. Имя и координаты не передаются в push: на экране блокировки достаточно текста о тестовой тревоге.

Серверную часть размещаем внутри Supabase. Отдельный постоянно работающий сервер для MVP не нужен. Серверные ключи остаются на сервере; приложение получает только публичную конфигурацию и сессию своего пользователя.

## Пять экранов

| Экран | Содержимое и действия |
| --- | --- |
| Вход | Регистрация, вход, подтверждение email, восстановление пароля |
| Главная | Тестовый SOS, текущая исходящая тревога, список активных входящих тревог, последнее состояние обращения к серверу |
| Доверенный контакт | Создание приглашения, ввод кода, принятие, направление связи, удаление связи |
| Тревога | Отправитель, время, тестовая точка, открытие внешних карт, подтверждение получателем, завершение отправителем |
| Настройки | Имя, состояние разрешения уведомлений, переход к системным настройкам, выход |

Вход показывается без действующей сессии. После входа доступны три основные вкладки: главная, контакт, настройки. Тревога открывается отдельным экраном из главной или push. Разрешение на уведомления запрашивается с объяснением при подготовке к получению сигналов, а не скрыто при запуске.

Если контакта нет, главная предлагает сначала добавить его. Отправка SOS без принятого контакта отклоняется также на сервере. После перезапуска приложение загружает актуальные активные тревоги из базы.

## Данные

| Сущность | Что хранит |
| --- | --- |
| Профиль | Идентификатор аккаунта и отображаемое имя; email и пароль обслуживает Auth |
| Приглашение | Кто приглашает получать свои сигналы, защищённое представление случайного кода, срок действия, состояние использования |
| Доверенная связь | Отправитель, получатель, время принятия и отзыва |
| Тревога | Идентификатор, отправитель, источник «симулятор», признак теста, тестовая точка, серверное время создания и завершения, ключ защиты от дублей |
| Получатель тревоги | Зафиксированный при создании получатель и серверное время его подтверждения |
| Телефон для push | Владелец сессии, push-токен и платформа; не идентификатор будущего кулона |
| Задание оповещения | Тревога, целевой телефон, состояние попыток, время следующей попытки и результат сервиса |

Это семь небольших таблиц в одной базе, а не семь сервисов. Отдельная запись получателя фиксирует, кому была адресована конкретная тревога. Смена контакта не перенаправляет уже созданное событие новому человеку.

## Серверные действия

1. Создать, проверить и принять приглашение; отозвать связь.
2. Создать тестовую тревогу.
3. Подтвердить просмотр получателем.
4. Завершить тест отправителем.
5. Зарегистрировать или отвязать push-токен текущей сессии.
6. Обработать задания оповещения и ответы push-сервиса.

Проверка кода приглашения не раскрывает посторонние профили. Коды случайные, одноразовые, действуют 24 часа; количество попыток ограничено. Самоприглашение запрещено. При принятии получатель видит отправителя и явно соглашается получать его сигналы. Ограничение одного контакта проверяется сервером даже при одновременных запросах.

Приложение может читать доступные ему данные, но критические изменения выполняются через серверные действия. Правила доступа в базе запрещают посторонним читать тревоги и изменять чужие подтверждения. Обновление собственного имени разрешается отдельно.

## Жизненный цикл SOS

1. Отправитель подтверждает тестовую отправку.
2. Приложение создаёт идентификатор попытки и обращается к серверу.
3. Сервер проверяет сессию, принятую связь и отсутствие другой активной исходящей тревоги.
4. В одной транзакции сохраняются тревога, получатель и задания оповещения для его зарегистрированных телефонов.
5. Только после сохранения приложение показывает «Сервер принял SOS».
6. Обработчик отправляет push. Его немедленный запуск ускоряет доставку; периодический серверный запуск подбирает оставшиеся задания независимо от открытого приложения.
7. Получатель открывает тревогу и подтверждает просмотр. Сервер проверяет его право и сохраняет время.
8. Отправитель получает обновление состояния и завершает тест.

Одновременно разрешена одна активная исходящая тревога на отправителя. Подтверждённая тревога остаётся активной до завершения. Повтор запроса с тем же идентификатором возвращает то же событие; параллельный новый запрос при активном событии возвращает его вместо создания дубля. Ограничения обеспечиваются базой и транзакцией.

Если ответ сервера потерян, показываем «Проверяем, принят ли SOS» и сверяем событие по тому же идентификатору. Не объявляем отправку неуспешной только из-за отсутствия ответа. Идентификатор сохраняется локально до выяснения результата. Автоматической отложенной отправки нового SOS после восстановления интернета нет.

## Оповещение и обновление экранов

Задание сохраняется вместе с тревогой, поэтому сбой после записи события не теряет намерение отправить push. Повторяются только временные ошибки, максимум три попытки отправки с увеличением интервала. Принятая сервисом попытка не повторяется только из-за отсутствия человеческого подтверждения. Проверка квитанций учитывает недействительные токены и ошибки передачи. Завершённые тревоги и отозванные связи не порождают новых попыток.

Успешная квитанция push-сервиса не равна доставке на экран и не равна просмотру. В пользовательском интерфейсе не выводим недоказанный статус «Доставлено». Ошибка оповещения и отсутствие зарегистрированного телефона получателя показываются отправителю; сохранённая тревога остаётся доступной внутри приложения.

Supabase Realtime используется для обновления активной тревоги и подтверждения, когда приложение открыто. При открытии экрана, возврате из фона и восстановлении соединения данные обязательно перечитываются из базы. Realtime не заменяет push и не хранит историю вместо базы.

Выход из аккаунта отвязывает push-токен от прежней сессии. При смене аккаунта токен не должен оставаться связанным с предыдущим пользователем. Детали тревоги проверяются сервером при каждом открытии, включая переход по старому уведомлению.

При отзыве связи получатель теряет доступ к событиям по этой связи, новые уведомления ему не отправляются. Активный тест этой пары завершается в той же транзакции; отправитель видит причину. Уже показанное системное уведомление отозвать гарантированно нельзя, но получить детали по нему после отзыва нельзя.

## Предлагаемая структура проекта

Ниже описана будущая структура. Папки и исходные файлы приложения на этапе проектирования не создаются.

| Путь | Ответственность |
| --- | --- |
| app/ | Маршруты пяти экранов, вкладки, служебные переходы входа |
| src/features/auth/ | Вход, сессия и восстановление доступа |
| src/features/contacts/ | Приглашения и доверенная связь |
| src/features/alerts/ | Тестовый SOS, главная, просмотр и подтверждение тревоги |
| src/features/settings/ | Имя, разрешения и выход |
| src/components/ | Только действительно повторяющиеся элементы интерфейса |
| src/services/ | Подключение Supabase, регистрация push и открытие внешних карт |
| src/theme/ | Общие цвета, размеры и оформление |
| assets/ | Иконка, заставка и необходимые изображения |
| supabase/migrations/ | Структура базы, ограничения, правила доступа и расписание обработки оповещений |
| supabase/functions/ | Серверные действия и обработчик оповещений |
| tests/ | Проверки критических правил и сценариев |
| docs/ | Согласованная архитектура и позднее инструкция проверки на телефонах |

Файл маршрута отвечает за открытие экрана; логика находится в соответствующей предметной папке features. Не создаём пустые заготовки, собственный универсальный фреймворк или отдельные слои без практической необходимости. Типы размещаем рядом с тем, к чему они относятся; общие выделяем только при реальном повторении.

## Подключение кулона позже

Симулятор отправляет события от авторизованного пользователя. Настоящий кулон получит отдельный способ регистрации и проверки устройства. После проверки оба источника смогут обращаться к общей операции создания тревоги.

На этом этапе не создаём реестр устройств, прошивку, MQTT, Bluetooth или фиктивные методы интеграции. Окончательный способ связи выбирается после выбора электроники. Формат тревоги уже отделён от экранов и push, но отсутствие переделок при неизвестном оборудовании не гарантируется.

## Что исключено

Кулон и Bluetooth; координаты телефона и фоновое слежение; история маршрутов; встроенная карта; больше одного контакта у отправителя; чат; оплата; подписки; SMS; автоматические звонки; веб-админка; AI-функции.

Технические записи сохраняются для текущего сценария и проверки работы. Пользовательский архив тревог не входит в MVP. Перед внешним пилотом отдельно определяется срок хранения и процедура удаления аккаунта и связанных данных.

## Проверка результата

- Два реальных телефона: Android отправляет iPhone, затем наоборот.
- Приглашение, явное принятие, отказ в доступе постороннему.
- Push при приложении в фоне и закрытом обычным способом; принудительная остановка проверяется отдельно без обещания доставки.
- Переход из push к правильной тревоге, подтверждение и завершение.
- Перезапуск приложения восстанавливает активное событие.
- Нет интернета, запрещены уведомления, нет push-токена, временная ошибка сервиса.
- Потерян ответ сервера и повторены запросы: одна тревога без ложного сообщения об успехе.
- Отзыв связи и смена аккаунта не раскрывают чужие сведения.
- Сбой обработчика после сохранения тревоги: оставшееся задание подбирается сервером.

Критические серверные правила проверяются автоматически; доставку и поведение мобильных ОС проверяем на устройствах. Успех сборки или статические тесты не доказывают получение уведомления человеком.

## Состояние решения

Стек и объём пяти экранов одобрены пользователем. Этот документ фиксирует предлагаемую архитектуру для следующего обсуждения. Код не написан, зависимости не установлены, облачные проекты не созданы. Следующий этап после просмотра документа — план реализации, если пользователь решит переходить к разработке.
