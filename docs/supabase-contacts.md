# Контакты: настройка Supabase и проверка

## Что выполнить

1. Открыть тот же проект Supabase, к которому уже подключено приложение.
2. В меню SQL Editor выбрать New query.
3. Скопировать ВЕСЬ файл `supabase/migrations/202610190001_contacts.sql` и нажать Run. Он должен завершиться без ошибки; обычно редактор выводит `Success. No rows returned`.
4. Не запускать в облаке тестовые файлы из tests/: они предназначены только для локальной временной базы.
5. Обновить приложение в Expo Go. Если сервер остановлен — выполнить `npm start`, затем отсканировать QR-код. `.env` не менять.

SQL создаёт две продуктовые таблицы (contact_invites и trusted_links), маленькую служебную таблицу счётчиков попыток (contact_rate_limits) и одну серверную функцию contact_action. Приложение вызывает её с сессией вошедшего пользователя. Доступ к таблицам напрямую закрыт, RLS включён. Secret key, service_role, Edge Functions и новые облачные сервисы для этого этапа не нужны.

Файл можно применить повторно без удаления записей. Если редактор сообщает о конфликте с уже существующей структурой, сохранить текст ошибки; не удалять таблицы вручную. В функцию не передаётся идентификатор текущего пользователя: сервер получает его из сессии.

## Поведение

- Код: 12 случайных символов 0–9/A–F, отображаются тремя группами; регистр, пробелы и дефисы при вводе не важны.
- Один код действует 24 часа, используется один раз. Новый отменяет старый.
- Открытый код возвращается только при создании, в базе хранится SHA-256. После закрытия экрана восстановить код нельзя: можно создать новый. Текст кода выделяется долгим нажатием; «Поделиться кодом» открывает системное меню.
- На аккаунт разрешено 5 попыток создания кода и 10 проверок/принятий за окно 15 минут. Проверка и последующее принятие расходуют по одной попытке. Неуспешные проверки тоже считаются.
- Не больше одного активного получателя на отправителя; получать можно от нескольких людей. Обратное приглашение принимается отдельно.
- Перед принятием видна только почта владельца действующего кода. Список связей доступен только их участнику.
- Любой из двух участников может удалить связь с подтверждением. Историческая запись остаётся отозванной и пропадает из активного списка.
- Список обновляется при открытии экрана, возврате приложения на передний план и по кнопке «Обновить». Push и постоянное наблюдение пока не подключены.
- Из-за неизвестного результата при обрыве соединения операция могла сохраниться на сервере. После ошибки нажать «Обновить», прежде чем повторять принятие или удаление.

## Проверка двумя аккаунтами

1. Войти аккаунтом A, открыть нижнюю вкладку «Контакты». В «Кому я отправляю сигналы» нажать «Создать приглашение», сохранить код.
2. Выйти и войти аккаунтом B (либо использовать второй телефон).
3. В «От кого я получаю сигналы» нажать «У меня есть код», ввести код и нажать «Проверить код». Должна появиться почта A; связи ещё нет.
4. Нажать «Принять приглашение». В «Я получаю сигналы» появится A.
5. Вернуться в A и нажать «Обновить»: в «Получает мои сигналы» должен отображаться B. Автоматической обратной связи нет.
6. Повторно использовать код, проверить собственный код и случайный код: ожидаются понятные ошибки.
7. Удалить связь с одного из аккаунтов. После обновления она исчезает у обоих; A может пригласить другого человека.
8. Проверить отключение интернета и повторное нажатие во время загрузки. Успех не должен показываться при ошибке; при неопределённом результате сначала обновить данные.

Просроченные коды, замену кода новым, ограничение попыток, приватность, одноразовость, удаление и уникальность получателя также проверяет `npm test` на локальном PostgreSQL (PGlite). Это не проверка вашего облачного проекта и не проверка настоящей параллельности запросов. База дополнительно обеспечивает ограничение уникальным индексом, а сервер сериализует изменения одного отправителя блокировкой.

Пока Confirm email отключён, использовать только тестовые аккаунты команды: email отображается как идентификатор аккаунта, а не как доказанно подтверждённая личность.
